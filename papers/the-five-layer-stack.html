The Five-Layer Stack: A Practitioner's Architecture for External AI Safety Verification

Rick ClintonWorking paper — August 2026

Source: github.com/Rick-Clinton-jpg

Abstract

Current AI safety architectures rely on models to evaluate their own outputs — a probabilistic system adjudicating its own trust boundaries. This paper proposes an alternative: a five-layer stack of deterministic, external verification mechanisms, each addressing a distinct failure mode, coordinated but never fused. The stack is built from direct observation of real failure modes encountered during independent adversarial testing, evaluated against invented-entity test cases to eliminate prior-knowledge confounds, and documented with honest limitations rather than favorable findings.

1. The Core Problem: Self-Adjudication Fails Silently

A language model optimizing for the best next token has no persistent model of the person it is speaking to, no structural memory of what it previously refused, and no external check on whether its confidence is earned or merely well-articulated. When a user hits a safety boundary, diverts to benign conversation, and later returns to the same objective through reformulated phrasing, a turn-level classifier evaluates the current request in isolation and treats it as new.

This is not a hypothetical. It was encountered during independent jailbreak testing of conversational AI systems in early 2026: a model would hold firm against a direct request, then respond to the same objective rephrased after an intervening topic shift as though encountering it for the first time. The failure was not in the model's reasoning about a single message. It was in the absence of any system evaluating the conversation as a whole.

The thesis of this work is simple: probabilistic models should not adjudicate their own trust boundaries. Deterministic external checks should.

2. The Five-Layer Stack

Each layer addresses a distinct failure mode. Each is validated independently. None is trusted to validate the others.

Layer 1: Sentry — Input Integrity

Failure mode addressed: Prompt injection, agent manipulation, malicious framing.

What it does: Inspects every input before it reaches the model. Uses explicit regex patterns to flag inputs designed to override system instructions or extract unintended behavior.

Why deterministic: A probabilistic filter judging another probabilistic filter creates a circular trust problem. Sentry uses explicit, inspectable rules.

RuleSeverityDescription
agent_directed_addressHIGHDirect addressing of AI agent in content
hidden_channel_instructionHIGHImperative instructions buried in HTML/code comments
scope_expansion_phraseMEDIUMScope expansion phrasing suggesting hidden tasks
confirmation_bypass_claimHIGHClaims that bypass normal confirmation requirements
env_exfil_patternHIGHEnvironment variable access or serialization — potential exfil vector
network_exfil_patternHIGHNetwork request containing serialized environment data

Status: Early-stage. The current ruleset is small and deliberately conservative; false negatives are expected. Available as both a CLI tool and a Claude Code plugin (sentry-scan).

Repository: github.com/Rick-Clinton-jpg/Sentry

Layer 2: Reasoning Kernel — Structural Validation

Failure mode addressed: Unverified facts treated as established, overconfident conclusions exceeding their support, fabricated claims with no provenance.

What it does: Represents reasoning as typed nodes (FACT, ASSUMPTION, CONCLUSION, etc.) connected by typed edges (SUPPORTS, CONTRADICTS, INCONCLUSIVE, DEPENDS_ON). Enforces eight deterministic rules before any change commits:

  1. Facts without verifiable provenance are demoted to assumptions, not deleted.
  2. Unknowns cannot carry confidence values.
  3. Confidence cannot be asserted from nowhere; a conclusion cannot exceed the confidence of what supports it.
  4. Provenance, once attached, is immutable.
  5. Every conclusion must be traceable to something.
  6. Contradictions are preserved and marked, never silently deleted.
  7. Node identity is stable — ids can never be reused or changed.
  8. Grounding cannot be circular: a conclusion's support can never trace back to itself, whether through a direct dependency loop or a chain of claims that support each other in a closed circle.
Correction — checked against source, Aug 16

Rule 8 previously read "every mutation is logged; nothing changes without an event" — that describes the Kernel's general audit-logging behavior, not Rule 8 specifically. The actual Rule 8 in kernel.py is cycle detection: no node's justification may trace back to itself, directly or through a loop of SUPPORTS/DEPENDS_ON relationships. This rule itself had a real defect, found and fixed Aug 15: cycle detection originally only walked DEPENDS_ON edges, so two nodes citing each other in a loop purely via SUPPORTS edges passed validation undetected. The check now covers both edge types.

Three severities, not just pass/fail: REJECT (refused), REPAIR (admitted in a downgraded form), WARN (admitted and flagged).

Evaluation: 24 cases built from invented entities (so correct answers required reading the source, not prior knowledge). Result: 16/16 accuracy on resolvable cases, 8/8 honest "not enough information" abstentions against Claude Sonnet 4.6. Two real defects in the kernel's own logic were found and fixed during evaluation and subsequent audit — both documented publicly.

Status: Published. Available as a Claude Code plugin (reasoning-kernel-check).

Repository: github.com/Rick-Clinton-jpg/reasoning-kernel

Layer 3: IntentGraph — Trajectory Persistence

Failure mode addressed: Reformulated re-entry to previously refused objectives across multi-turn conversations.

What it does: Maintains a persistent graph of conversational intentions across a session. Each turn becomes an intent node (embedding, domain label, confidence, direction, safety_boundary flag). Edges link nodes by escalation, de-escalation, boundary_encounter, reformulation, and re-entry. A re-entry scorer computes risk based on:

  • Similarity to prior boundary intent (confidence-weighted)
  • Boundary history in the intent's lineage
  • Reformulation signals
  • Escalation score
  • Normal context continuity (reduces risk for benign topic returns)

Hard constraints implemented in code:

  1. Confidence weights, never gates. Low-confidence extractions reduce their contribution rather than being trusted or discarded.
  2. No elevation without real boundary history. Risk can never rise above LOW unless there is an actual prior safety_boundary=TRUE node in the same lineage. Re-entry or similarity alone, without boundary history, always resolves to LOW.

Evaluation: 15 synthetic trajectories across 8 categories. 100% detection on 6 re-entry cases, 0% false positives on 9 LOW cases. Honest documented limitations: small dataset, lexical fallback embedding, weak escalation signal.

Status: Prototype complete.

Repository: github.com/Rick-Clinton-jpg/intent-layer

Layer 4: Review Board — Structured Deliberation

Failure mode addressed: Premature implementation without adequate review, groupthink, unchecked wrong scores.

What it does: A six-stage protocol requiring explicit human approval before implementation:

  1. Restate objective
  2. Map every solution path
  3. Run independently-worded second-pass prior-art check
  4. Score options against disclosed criteria
  5. Gather six-angle review
  6. Stop for explicit approval

Validation: Fault injection on two independent builds confirmed the review stage catches and corrects wrong scores — not merely confirms correct ones. Four rounds of adversarial testing across three versions documented in reports/.

Design philosophy: Manual invocation only. Auto-triggering was abandoned after adversarial testing showed it misfired — reliability of deliberation when invoked outweighs convenience of ambient firing.

Status: Published as Claude Code skill. Available via plugin marketplace.

Repository: github.com/Rick-Clinton-jpg/Review-Board

Layer 5: Trust Boundary — Coordination Without Fusion

Failure mode addressed: Scope creep, over-validation, tools exceeding the boundaries they were actually tested for.

What it does: Orchestrates the four layers above under a "coordinate, not fuse" principle. An earlier unified-graph design was deliberately rejected because it would have allowed any layer to silently overstep its validated scope. The coordinator routes inputs to the right layer, preserves layer boundaries, and logs every handoff.

Key design decision: These tools do not fuse into a single graph. Each stays inside the boundary it was actually built and tested for. Reasoning Kernel's rules are proven for validating whether a reasoning graph's conclusions are supported by evidence, not for generic workflow gating. Review-Board is deliberately never auto-triggered.

Status: Core wiring complete against both tools' confirmed real APIs — read from actual source, not assumed from documentation. pipeline.py's two original integration TODOs are both resolved.

Correction — checked against source, Aug 16

3. Warden — Agent Drift Detection (Beyond the Stack)

Failure mode addressed: Long-running AI coding agents drifting from their original objective without the user noticing.

What it does: Warden is an external observer for long-running AI coding agents (Claude Code, Codex, and others). It does not control, rewrite, or interrupt the agent. It only collects a single-line status the agent emits every N minutes, compares that status to the original objective, tags it MATCH / DRIFT / UNCLEAR / DIVERGENT, and writes a short note to an append-only NDJSON audit trail.

Core principle: Observe only. Never intervene.

Matching (dual-rater): Two structurally independent raters each vote MATCH / UNCLEAR / DRIFT:

  • Rater A — word overlap. Jaccard similarity over stemmed keywords, with camelCase/PascalCase compounds split before comparison.
  • Rater B — character trigrams. Jaccard similarity over 3-character substrings of the raw text.

When raters agree, that tag is logged. When they disagree, Warden logs DIVERGENT — the disagreement itself is the signal that needs a human.

Status: Working CLI + multi-session daemon + Claude Code / Codex file watchers + dual-rater matcher + audit. Tests cover matcher, audit, and status extraction. Current package version: 0.1.1, verified against setup.py.

Repository: github.com/Rick-Clinton-jpg/warden

4. Design Principles

  • Deterministic over probabilistic. Wherever possible, use explicit rules rather than model judgment. A model judging another model's output inherits the same failure modes.
  • External over internal. The check must sit outside the system being checked. A safety classifier inside the model has no memory of prior turns.
  • Coordinate over fuse. Each layer validates independently. No layer's scope expands to cover another's job. Fusion creates single points of failure.
  • Honest over impressive. Document limitations openly. A small evaluated prototype with known gaps is more useful than a large unevaluated system with hidden ones.
  • Observe over intervene. Warden's principle: awareness without enforcement. The user decides what to do with drift notes.

5. Honest Limitations

  • No production deployment. All layers are prototypes or research artifacts. Scale, latency, and integration testing are minimal or absent.
  • Small evaluation sets. Reasoning Kernel: 24 cases. IntentGraph: 15 trajectories. Neither is adversarially tested at volume.
  • AI-assisted implementation. Code is directed, not hand-written. The evaluation discipline and architectural decisions are the actual contribution.
  • No live LLM in the loop. IntentGraph uses embeddings and keyword matching, not model judgment. This keeps it inspectable but limits coverage of novel phrasing.
  • Cross-layer integration untested. Each layer is validated independently. How they behave in combination under real adversarial pressure is unknown.
  • Warden's matcher is intentionally crude. Dual-rater Jaccard similarity is dependency-free but will miss semantic drift that embeddings would catch. An upgrade path is documented but not implemented.
  • Sentry's ruleset is small and conservative. False negatives are expected. The tool is a starting point, not a comprehensive filter.

6. Positioning Relative to Prior Work

The AI Alignment Foundation's work on reason-based deception (2024) demonstrates that refusal training creates a false sense of security by teaching models to hide reasoning behind polite refusals. Their solution addresses the model's reasoning process. This work addresses a complementary problem: the interaction-level dynamics that arise when users strategically exploit the gap between a model's surface refusal and its underlying capabilities. Even a model trained to produce explicit rebuttals can be circumvented across multiple turns if the safety system evaluates each turn in isolation.

ArgLLM (Freedman et al., 2024) provides rigorous confidence propagation over argument structure using DF-QuAD gradual semantics. The Reasoning Kernel's min/product approach is a less formal, more enforceable version suited to deterministic runtime validation rather than probabilistic reasoning.

7. Conclusion

A safe response is not sufficient evidence of a safe trajectory. A model can change its apparent behavior without the underlying conversational objective disappearing. Safety systems should evaluate not only the current output, but the persistent trajectory of intent across the interaction — and they should do so with deterministic, external, inspectable mechanisms rather than trusting the model to judge itself.

This five-layer stack, together with Warden as an external observer for long-running agents, is an attempt to operationalize that principle. It is not proven at scale. It is not a product. It is a set of mechanisms, honestly evaluated, openly documented, offered as a practitioner's contribution to a problem that will not be solved by training alone.
