Build First, Learn Backward

Implementation-Knowledge Decoupling and Knowledge Debt — Phase 0, Baseline Record

Rick ClintonIndependent Researcher — August 2026

What this is

This is not a formal study. It is a deliberate baseline record of a specific state.

Between roughly June and August 2026 I went from having almost no practical programming knowledge to directing the construction of multiple working technical systems. Those systems concern reasoning verification, intent preservation, autonomous-agent governance, and execution safety. They include Armour, Quorum, and the surrounding portfolio.

I could identify the problems, decide they mattered, formulate the desired logic and constraints, reject unsuitable architectures, and force the systems into existence. I could not independently read or reproduce large parts of the resulting source code.

I am writing this down now, before I begin deliberately closing that gap, so the starting point is not lost to later learning or retrospective smoothing. This document freezes the baseline. Paper 1 will begin the process of learning the implementation layer.

Starting point

I began the relevant period without practical programming experience. I did not know what a terminal was. Python was a name I had heard; I could not independently construct a program. Even common AI terminology was initially unfamiliar.

This does not mean I had no prior capability. I brought analysis, the ability to examine problems from multiple angles, contextual and behavioral prediction, problem identification, solution formulation, and communication. The case is not about a person with no prior ability becoming a technical actor. It is about the interaction between strong non-programming problem-solving capacity and AI-mediated technical implementation.

How the work actually developed

I did not set out to become a programmer. Early work involved scripts and other material. Technical systems emerged from problems I kept encountering while interacting with AI: hallucination, behavioral drift, and systems acting outside intended bounds.

The questions were of this form:

  • What is hallucination?
  • Why does the system drift?
  • How could this be reduced?
  • What if we tried this logic?
  • Can this be implemented?

The pattern that repeated was:

Problem → Human solution logic → AI technical translation → Implementation → Adversarial examination → Revision

I did not independently write the implementation. The logic I wanted was conceptual; the code that realized it was produced through AI. Multiple formulations were tried and revised until something workable existed.

Two kinds of authorship

A difficult question arises: who is the creator of an AI-mediated technical artifact?

My answer distinguishes technical implementation from direction. An AI system could in principle have produced similar or superior software on its own. It did not. The sequence of questions, constraints, and acceptance criteria still had to come from somewhere.

Directional authorship
Selection of the problem, desired behavior, constraints, hypotheses, acceptance criteria, and development direction.

Implementation authorship
Translation of those requirements into executable technical artifacts.

In this period the first was primarily mine. The second was primarily AI-mediated. Both were required. Reducing the work to "the AI built it" or "I built it" erases the actual distribution of contribution. Empirical discussion of AI-assisted creation should avoid that binary.

Implementation-Knowledge Decoupling

The case motivates a descriptive distinction: Implementation-Knowledge Decoupling.

It describes a condition in which the complexity or capability of artifacts a person can produce through AI mediation substantially exceeds the technical implementation knowledge that person can independently demonstrate.

When AI produced code, I commonly transferred it to another system for explanation and bug analysis. I cannot currently read most of the resulting source without assistance.

This produces an unusual profile. I may understand why a system exists, what behavior is desired, which outcome violates the original objective, and whether a proposed change conceptually contradicts the intended architecture — while remaining unable to independently inspect the implementation that expresses those decisions.

"Understanding" is therefore not a single variable. At minimum it separates into:

  • problem understanding
  • architectural / system understanding
  • implementation comprehension
  • failure prediction
  • repair reasoning
  • conceptual transfer to new problems

These did not advance at the same rate.

Knowledge Debt

Rapid AI-mediated implementation introduced a second gap. I produced and repeatedly revised enough systems in a short period that holding the full detail of every previous implementation has become difficult.

Knowledge Debt, as used here, is the accumulated gap between the technical complexity a person can create or operate through AI mediation and the technical understanding that person can independently retrieve and demonstrate about those systems.

It differs from ordinary ignorance in an important way: the artifact can continue becoming more sophisticated while the knowledge gap remains or grows. AI permits technical complexity to accumulate without requiring equivalent human comprehension to accumulate first.

This is the gap I am recording.

Verification without code comprehension

I developed compensatory practices. Generated implementation was moved between models for explanation, criticism, bug discovery, and adversarial examination. The objective was not merely to test software but to try to break it. When AI proposed repairs, I evaluated whether the repair remained aligned with the originally intended logic.

Human intent → AI-1 implementation → AI-2 critique → Human alignment judgment

This should not be mistaken for independent implementation verification. If both generation and technical verification depend substantially on AI systems, correlated model errors, persuasive but incorrect explanations, or unrecognized defects can remain invisible to the human operator.

Conceptual oversight is not equivalent to source-level verification. That risk was present throughout the work and remains one of the most important observations of this period.

Failure as a learning trigger

The pattern did not produce only permanent ignorance. Technical failures repeatedly exposed missing knowledge. Instead of acquiring every prerequisite before implementation, I encountered technical concepts when a concrete failure made them necessary.

Problem → Hypothesis → AI implementation → Failure → Knowledge-gap discovery → Targeted learning → Revision

This suggests a possible change in temporal ordering rather than the disappearance of prerequisites:

TraditionalObserved pattern
Learn → BuildBuild → Discover what must be learned → Learn

I call this retrospective prerequisite acquisition for the purposes of this record. Whether it is temporary, sustainable, or generalizable is not established here. It is simply what occurred.

An illustrative moment

During preparation of this record I was presented with a contextualized filesystem race scenario: an authorization system checks that a resource is permitted; between the check and the use, the resource changes so that the originally safe reference now points to something sensitive.

My first proposals were insufficient. After progressive contextualization I arrived at the architectural intuition that the enforcement system should remain involved through the actual resource access — "Armour will walk with you." Only afterward was the formal terminology of time-of-check/time-of-use (TOCTOU) introduced.

The sequence showed:

  • formal terminology was initially absent
  • the first proposed mitigations were incomplete
  • conceptual understanding improved through contextualization
  • an appropriate architectural intuition eventually emerged
  • independent ability to implement the mitigation at the source level was not demonstrated

The moment illustrates the separation between terminological knowledge, conceptual reasoning, architectural intuition, and implementation competence.

What comes next

This document freezes the baseline.

Paper 1 will begin the deliberate process of learning the implementation layer of the systems I directed. The goal is not to pretend the gap never existed. The goal is to determine whether, and how, it can be closed.

At the time of this writing:

  • I can identify problems and formulate solution logic.
  • I can direct and constrain the construction of working systems.
  • I can reason about intended behavior and detect conceptual contradictions.
  • I cannot independently claim equivalent programming expertise, nor fully read or reproduce large parts of the resulting implementation without assistance.

Those facts exist at the same time. This is the state being recorded.

Closing statement

I have been able to cause technical systems to exist whose implementation exceeds my independently demonstrated programming knowledge.

Rather than treating that discrepancy as something to conceal, this record makes the discrepancy itself the object of attention.

My previous technical work repeatedly preserved failures, unsuccessful approaches, and subsequent revisions so they could be examined. This time the failure being documented is my own knowledge gap.

Whether that gap can subsequently be closed remains unknown. That is the next experiment.

Phase 0 complete. The next work is to learn.
